# Project Workflow

This file describes the default team process for the project course repository.

## 1. Planning

At the start of each iteration:

- define the goal,
- list the tasks to complete,
- break large tasks into smaller issues,
- estimate priority and effort,
- assign ownership to team members.

## 2. Task tracking

Use GitHub issues for concrete work items.

Each issue should contain:

- clear title,
- objective,
- acceptance criteria,
- dependencies or blockers,
- assignee,
- due date if relevant.

## 3. Execution

- Start from the latest `main` branch.
- Create a short-lived feature branch.
- Keep work in small, reviewable changes.
- Commit in logical chunks.
- Update documentation when behavior or setup changes.

## 4. Review

Before merging:

- ensure the task matches the acceptance criteria,
- verify any tests or checks pass,
- request a review from a teammate,
- address feedback and document the result.

## 5. Delivery

The main branch should represent the current working version of the project. It should be kept in a usable state for the team and for course deliverables.

## 6. Meeting rhythm

Suggested cadence:

- weekly planning session,
- short progress sync during the week,
- end-of-sprint review or retrospective.

## 7. Good practices

- Keep tasks small enough to finish without indefinite drift.
- Do not start without a clear acceptance criterion.
- Write decisions down when they affect scope, architecture, or process.
- Keep communication explicit and timely.

## 8. Definition of ready

A task is ready to start when:

- the problem is unambiguous,
- the acceptance criteria are clear,
- required dependencies are identified,
- ownership is assigned.

## 9. Definition of done

A task is complete when:

- implementation is finished,
- the result has been validated,
- documentation has been updated if needed,
- the pull request is reviewed and merged.
